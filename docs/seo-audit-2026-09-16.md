# SEO audit — jimmyvanveen.com

- **Date:** 2026-09-16
- **Practices snapshot:** `~/.claude/skills/seo/PRACTICES.md`, dated 2026-08-02 (in-window; no refresh pass run)
- **Goal driving priority:** name-search results for "jimmy van veen" — the site already ranks #1
  for the name, so the problem is _presentation and entity identity_, not position.
- **Evidence basis:** live responses from `https://www.jimmyvanveen.com` fetched 2026-09-16
  (not framework defaults assumed to work).

## Headline observation

Every HTML page on the live site serves the identical `<title>Jimmy Van Veen</title>` with **no**
`<meta name="description">`, **no** `rel="canonical"`, and **no** structured data of any kind.
`app/root.tsx` sets `meta` to a single `{ title: "Jimmy Van Veen" }` and no child route except
`/privacy` overrides it. In React Router v7 a child `meta` export _replaces_ the parent's, so
`/`, `/blog`, and every `/blog/:slug` inherit that one title verbatim.

That is a documented title-rewrite trigger (boilerplate + vague + repeated across pages), and it
is the direct cause of both symptoms in the reported SERP: the bare "Jimmy Van Veen" title on
every result, and Google inventing its own snippet — the "MCP server for YNAB (You Need A
Budget) …" text is scraped verbatim from the _Selected work_ project rows on the home page,
because there is no description to use instead.

## Gap ranking — (evidence strength × impact) ÷ effort

1. **Per-page titles + descriptions** — strongest evidence, highest impact on the reported symptom, low effort
2. **robots.txt** (with sitemap + AI-crawler decision) — strong evidence, low effort
3. **Sitemap honesty** — drop `changefreq`/`priority`, use real per-page mtime or omit `lastmod`

7. **About page + `ProfilePage`/`sameAs`** — the actual disambiguation lever; blocked on owner-supplied identity facts

9. **Apex DNS A record** — owner action at the registrar

- No `Person` JSON-LD as a standalone type — not a rich-result type; `ProfilePage` is the supported form.

## Follow-up: /about and a latent SSR bug

### The About page

`/about` now exists, carrying `ProfilePage` → `mainEntity: Person` with `name`, `jobTitle`,
`description`, `worksFor`, `url`, and `sameAs`. This is the item that actually attacks the
disambiguation problem: the site ranked first for the name while never stating who its subject
was, so there was nothing for Google to attach the name to.

`sameAs` lists only GitHub and Bluesky — the two profiles already linked from the site's own
footer and therefore verifiably his. **No values were guessed.** A LinkedIn URL and a portrait
are still needed; both were requested from the owner rather than inferred.

Built on the existing `blog-page` / `blog-post-hero` / `prose-editorial` classes, so it adds no
CSS. Wired into the top bar, the mobile sheet, the home-page footer, and the sitemap.

### The bug it surfaced

Verifying the served HTML — rather than trusting that the page "worked" — caught this:

> A route exporting `clientLoader` with `clientLoader.hydrate = true` and **no server `loader`**
> makes React Router render the `HydrateFallback` during SSR instead of the route component.

The response still carries a 200 and the correct `<title>`, and the page looks perfect in a
browser once JS runs. But the served HTML body is **empty**, and that is all a crawler ever sees.

`/privacy` has been shipping in exactly that state on `main` — confirmed against production:

```
curl -s https://www.jimmyvanveen.com/privacy | grep -c "Information We Collect"   →  0
```

`/about` was written to the same pattern and would have shipped the same way — an empty body on
the one page whose entire purpose is to be read by a search engine. Both now export a server
`loader`, and `app/routes/hydrate-loader.test.ts` fails the build if any route sets
`clientLoader.hydrate = true` without one. The guard was negative-tested: removing the loader from
`about.tsx` makes it fail with the explanatory message, and restoring it makes it pass.

This is the single most valuable thing the audit turned up, and no amount of reading the source
would have found it. It is the reason the practice file insists that served-HTML verdicts cite
observed responses rather than framework defaults assumed to work.

## Follow-up: Open Graph tags (not an SEO measure)

Added at the owner's request after the audit closed. **This changes nothing about the audit's
verdict**: Open Graph and Twitter card tags remain unsubstantiated as a Search practice, because no
in-window search-engine primary source documents them as a ranking or appearance signal. They earn
their place for a different reason — a link to this site pasted into Slack, iMessage, Bluesky, or
LinkedIn should render a title, a sentence, and a picture instead of a bare URL.

Emitted from the same `buildMeta` helper, so a route cannot get a canonical without also getting a
share card:

- `og:type` — `article` on blog posts, `website` everywhere else.
- `og:site_name`, `og:title`, `og:url` — mirror the resolved title and canonical.
- `og:description` — mirrors the meta description, and is **omitted** when there is none, for the
  same reason the meta description is.
- `og:image` / `og:image:alt` — a post's own Contentful image when it has one, otherwise the
  Talladega plate the home page already shows. `absoluteUrl` normalises site-relative paths and
  Contentful's protocol-relative `//images.ctfassets.net/…` form, since preview fetchers reject
  anything that is not absolute https.
- `twitter:card` — `summary_large_image`. No `twitter:title`/`description`/`image`: X falls back to
  the `og:*` equivalents, so duplicating them is dead weight.

The share image costs preview fetchers 381 KB rather than 3.39 MB, because the LCP re-encode landed
first.

**Verified in served HTML** across `/`, `/about`, and a post — `og:type` correctly flips to
`article` on the post. **Not yet exercised against real data:** no post in Contentful currently has
its `image` field set, so all nine fall back to the site plate. The Contentful branch is covered by
unit tests but has never run against a populated field. Setting a hero image on a post in Contentful
will pick it up with no code change.

## Follow-up: second review round

### JSON-LD injection — checked, already safe

Raised as a question rather than a defect: the `Article`/`ProfilePage` blocks interpolate
Contentful strings, and if any ever contained the literal `</script`, the browser would close the
script element early and parse the rest as markup. `JSON.stringify` alone does not prevent that.

**Verified empirically, not by reading docs.** React Router's `"script:ld+json"` handler pipes the
serialized JSON through `escapeHtml` (`react-router/dist/.../ssr/markup.js`), which replaces `<`,
`>`, `&`, U+2028 and U+2029 with unicode escapes — the standard mitigation. Confirmed by injecting
a live payload into the `/about` description, building, and reading the served HTML:

```
"description":"XSSPROBE</script><img src=x onerror=alert(1)>END"
```

Every `<` and `>` is escaped, the script element does not close early, and no injection occurs.
**No change needed**, and nothing should be added in `buildMeta` — double-escaping would corrupt
legitimate angle brackets in post descriptions.

### Blog-post coverage

`e2e/crawler-surface.spec.ts` cannot render a `/blog/:slug` page: the Playwright suite builds with
`DISABLE_CONTENTFUL_RUNTIME=true`, so no posts exist to render. Stubbing a post fixture into the
production caching layer purely to satisfy a test is a worse trade than testing the logic directly,
so the post route is covered at the unit level instead:

- `articleJsonLd` is now a pure exported function in `app/utils/seo.ts` rather than an object
  literal inlined in the route, asserted in `seo.test.ts` — author fallback, blank-author handling,
  description omission, absolute `mainEntityOfPage`.
- `post-hero.test.tsx` asserts the rendered byline, including that a blank author falls back to the
  same name `articleJsonLd` uses. If the two ever disagree, the markup would be claiming an author
  the page does not show.

**The honest residual gap:** nothing asserts a real post's _served HTML_ end to end. The unit tests
cover the logic that produces it, and `crawler-surface.spec.ts` covers the served HTML of every
route that can render without a CMS. Closing the last gap needs either a Contentful fixture in the
e2e build or a live smoke check against the deploy preview; neither was worth the production-code
contortion today, and it is recorded here rather than left implied.

### Third review round: a real bug in the byline

Review caught a genuine divergence, not a style point. `PostHero` resolved the author with `??`
while `articleJsonLd` used `||`. Those agree on `null`/`undefined` and disagree on `""` — and a
Contentful Symbol field that was filled in and later cleared yields exactly `""`. The result would
have been a post rendering `By  · July 5, 2026` with a blank name, while the `Article` markup
claimed "Jimmy Van Veen" as the author.

That is precisely the failure this PR's structured-data work exists to prevent: markup asserting
something the page does not show. It survived because the test coverage was asymmetric —
`seo.test.ts` exercised `author: ""` but `post-hero.test.tsx` only tested `undefined` and a
non-empty name.

Fixed at the root rather than by matching operators: both call sites now go through a single
exported `resolveAuthor` in `app/utils/seo.ts`, which also trims, so whitespace-only authors fall
back too. Drift is now structurally impossible.

The guard is an invariant test rather than another example-based one — for each of `undefined`,
`""`, `"   "`, and a real name, it asserts the rendered dateline contains the same string the
`Article` markup claims. Negative-tested by reintroducing `??`: four tests fail with
`expected 'By  · July 5, 2026' to be 'By Jimmy Van Veen · July 5, 2026'`.

### Fourth review round: two consistency defects, same class as the third

Both found, both fixed, both now guarded.

**1. `buildMeta` passed a blank title straight through.** `homeTitle ?? \`${title ?? SITE_NAME}${TITLE_SUFFIX}\``used`??`, so an empty-string title produced `" · Jimmy Van Veen"`— a leading separator with no
title. Exactly the divergence the`resolveAuthor`fix addressed one round earlier, in a function
whose own`description`handling had always treated`""` as absent.

Fixing it surfaced a second trap that the review did not mention and the first attempt walked
straight into: falling back to `SITE_NAME` _before_ appending the suffix yields
`"Jimmy Van Veen · Jimmy Van Veen"`. The suffix has to be skipped entirely rather than applied to a
defaulted title. The original `??` form had the same wart whenever no title was passed —
unreachable today because every route supplies one, but wrong.

**2. The home page's `WebSite.url` disagreed with its own canonical.** `canonicalUrl("/")` returns
`SITE_URL` with no trailing slash, deliberately and unit-tested, so one page cannot claim two
identities. The `WebSite` block on that same page asserted `${SITE_URL}/`. The e2e test checked
only `site.name`, so it never looked.

It now derives from `canonicalUrl("/")` and the e2e test asserts the JSON-LD `url` equals the
canonical actually present in the served HTML, rather than hardcoding a second copy of the
expected string. Negative-tested by reintroducing the trailing slash:
`Expected: "https://www.jimmyvanveen.com"  Received: "https://www.jimmyvanveen.com/"`.

**The pattern across rounds three and four is worth naming:** every defect found after the initial
audit was a _consistency_ defect — two places computing the same value differently — and none was
caught by the type system, because both sides typecheck. The fixes that stuck were the ones that
removed the second copy (`resolveAuthor`, `canonicalUrl("/")`) rather than making the two copies
agree.
